# Releases, in-app updates, versioning

## Releases & in-app updates (Android)
- **CI status:** staging is switched (2026-11-07: `-staging` pre-releases + `publish-release.cjs`, still also App Distribution). Main's `deploy.yml` publishes GitHub Releases from the next `development` → `main` merge on (1.3.0 / build 90 was the last App Distribution release and the first with in-app updates). Its checkout uses secret `RELEASE_PUSH_TOKEN` (a token of an account allowed past branch protection): without it the version bump can't reach main / development and that step fails after the release has gone out.
- **Releases are GitHub Releases** (public repo): `main` → `vX.Y.Z+BUILD` (latest), `staging` → `vX.Y.Z+BUILD-staging` (pre-release; staging still also goes to App Distribution). CI deletes older builds of the same version per channel, so GitHub keeps one release per x.y.z. Production no longer uses Firebase App Distribution (PR builds attach the APK to the run).
- After each release `scripts/publish-release.cjs` writes `config/release.{prod|dev}` = `{ version, build, apkUrl, size, notes, minBuild? }` (public-read doc — `config/app` holds the TMDB key), and sends FCM data `{ type: app_update }` to topic `app-updates-{channel}`. `[force-update]` sets `minBuild` (+ legacy `config/app.minBuild{Dev,Prod}`).
- App: `services/appUpdate.ts` (release listener, `downloadApk` via expo-file-system legacy with progress, `installApk` → Android installer via expo-intent-launcher + `REQUEST_INSTALL_PACKAGES`), `stores/updateStore.ts` (offer / skip / download state, debug simulation), `components/UpdateGate.tsx` + `modals/UpdateSheet.tsx` (regular update = bottom drawer over login / app; forced = full-page `Modal` (edge to edge, same content as the drawer) over login / app, the app stays mounted below with its cache, touch-blocked, never signed out; back / Close App = `BackHandler.exitApp`; web has no update UI). Build numbers come from `app.json` `versionCode` (`APP_BUILD`) — CI publishes the same number. Channel = `EXPO_PUBLIC_RELEASE_CHANNEL`, dev in local dev builds (`UPDATE_CHANNEL`).
- Notifications: native local module `app/modules/update-notification` (Kotlin; `services/updateNotifications.ts` calls it, the FCM background handler in `index.ts` too). Custom RemoteViews layouts so they wear the app's theme — Android's standard templates pick every colour themselves, and only foreground-service cards may colour their background: offer ("vx is available", red Install) → `UpdateDownloadService` (dataSync foreground service: dark colorized card, white text, red progress bar, red Cancel; expanded: the drawer's dial, its ring spun by the system via an indeterminate `ProgressBar`) → "downloaded" card whose tap / Install opens the installer directly (`UpdateFileProvider`). Same APK file as the drawer (`watchloom-update.apk` in the cache). Every `UpdateDownloadService` start comes from `startForegroundService`, so each `onStartCommand` branch calls `startForeground` before it may stop (a stop first = `ForegroundServiceDidNotStartInTimeException` crash). Needs a native rebuild when changed.
- Server: `requireCaller` → `hooks/appVersionGate.ts` refuses app builds below `config/release.{channel}.minBuild` (callables carry `appBuild` + `releaseChannel` via `tagCallable`; builds that send none are refused once any minimum exists). Firestore isn't build-checked in rules; a refused callable just fails ("Update the app to keep using it") — never a sign-out.
- Test pushes from a PC: `sendTestPush` (HTTP, secret `TEST_PUSH_KEY` in header `x-test-push-key`) → `scripts/send-test-push.sh [email] [prod|dev]`. Sends the channel's current release as a `test` push (shown even on that build).
- An updated app can't relaunch itself (Android 10+); the installer's Open button / the notification do it.
- Test flow: `docs/testing/in-app-update.md`, `scripts/release-test.cjs` (dev channel only), Settings → Updates (test) on staging/dev builds.

## Version rules (from Hard rules)
- **Version bump:** never reset buildNumber/versionCode to 1 — they climb separately per branch. Staging's `bump-build.yml` adds +1 per staging build (version string untouched); production's `deploy.yml` sets prev main build + 1. Version strings are handled by `scripts/release-version.cjs` (below).
- **Versions are automatic (`scripts/release-version.cjs`, `deploy.yml`):** staging is always main + 1 patch. A staging → main merge makes main inherit staging's number, then CI moves staging up one patch (merges main into staging with `-X ours`, and syncs the version files to development). A hotfix pushed straight to main (version unchanged) gets a patch bump; `[minor]` / `[major]` in the commit message or `bump:minor` / `bump:major` PR label still bump main from its previous version (staging then = that + 1). Before a merge to `main`, tell the user what the number will be (patch = fixes/polish, minor = new features/screens, major = redesign/breaking) and set staging's version higher by hand only for that case. Add `[force-update]` only when old builds must stop working (asks the user first).
